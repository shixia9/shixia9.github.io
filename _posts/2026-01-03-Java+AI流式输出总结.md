## 前言

> 接入大模型流式输出半年多，踩过不少坑。SSE、WebFlux、WebSocket都用过一些，每种方案各有优劣，选对了事半功倍，选错了处处受限。本文尝试从一个开发者的视角，聊聊这几种流式方案的本质差异和选型心得。

先说总结

| 技术方案                  | 通信方式 | 协议           | 复杂程度 | 并发性能 |
| --------------------- | ---- | ------------ | ---- | ---- |
| SSE                   | 单向   | HTTP 1.1     | ⭐⭐   | 一般   |
| WebFlux+Flux          | 单向   | HTTP 2 + 响应式 | ⭐⭐   | 好    |
| WebSocket             | 全双工  | TCP          | ⭐⭐⭐  | 较好   |

比较流行的Java+AI应用所用的流式输出套路大致为以上4种，简单来说，SSE它简单可靠、相比WebSocket更加轻量，而且浏览器原生支持自动重连；WebFlux+Flux的实现具有更强的并发能力，它的线程模型是事件驱动而非同步阻塞；WebSocket的同步性就相对更高了，因为它是全双工通信，更适合一些实时性较高的场景。

传统HTTP是“一问一答"，等模型生成完再返回，用户盯着空白屏幕等10秒，体验极差；流式输出的本质是把“等待时间"转化为“交互时间"，边生成边显示，用户看到的是打字机效果，心理上感觉更快。但流式输出不只是能用就行，背后藏着几个关键考量：
+ 100人同时对话，线程扛得住吗？（并发性）
+ 网络抖动，流断了怎么恢复？（断线重连）
+ 每个连接占多少线程和内存？（资源消耗）
+ 前端适配
+ 出现问题能否快速定位

## SSE Emitter

SSE（Server-Sent Events）是基于HTTP长连接的**单向推送协议**，服务端持续吐数据，前端通过`EventSource`API接收。
协议相对简单：
```plaintext
HTTP/1.1 200 OK
Content-Type: text/event-stream
data: 第一段内容
data: 第二段内容
event: done
data: [DONE]
```
优点很明显：
1. Spring MVC原生支持，`SseEmitter`几行代码搞定
2. 前端`EventSource`的API相对简单，不需要额外库
3. 天然支持断线重连
缺陷就是它的线程阻塞模型，每个连接占用一个线程，当并发量上来时就扛不住；而且前面说过它是服务端->客户端单向通信的，因此想交互就得再开个HTTP请求；得自己处理超时

因此，对于传统的SpringBoot项目，并发量要求并不高（<1000）的情况下，快速上线优先，SSE就是优先级比较高的选择。

### ResponseBodyEmitter

提了SseEmitter就不得不想到ResponseBodyEmitter，二者是继承关系，SseEmitter是 ResponseBodyEmitter的特化版本，专门为SSE协议设计。它们都来自包`org.springframework.web.servlet.mvc.method.annotation.*`下。
```java
public class SseEmitter extends ResponseBodyEmitter {}
```
它们的核心区别为RBE更原始，很多东西要自己设置，而SseE针对SSE协议进行了标准化设计，各有取舍吧，具体如下：

|              | ResponseBodyEmitter | SseEmitter                 |
| ------------ | ------------------- | -------------------------- |
| 输出格式     | 原始文本，自己控制  | SSE标准格式`data: xxx\n\n` |
| Content-Type | 自己设置            | 自动`text/event-stream`    |
| 前端接收     | 普通流读取          | EventSource API            |
| 灵活性       | 高，自己控制一切    | 低，只能走SSE协议          |

### 简单实现

```java
@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter chat(@RequestParam String question) {
    SseEmitter emitter = new SseEmitter(60_000L);
    // 异步执行，避免阻塞请求线程
    CompletableFuture.runAsync(() -> {
        aiService.streamChat(question, chunk -> {
            emitter.send(SseEmitter.event().data(chunk));
        });
        emitter.complete();
    });
    
    return emitter;
}
```

## WebFlux+Flux

WebFlux是Spring的响应式栈，基于Reactor；`Flux`是一个**异步数据流**，支持背压Backpressure——消费者处理不过来时，可以通知生产者慢点发。和SSE的根本区别在于：SSE是**一个连接一个线程**，而WebFlux是**一个事件循环处理所有连接**。

WebFlux的优势就在于：
1. 非阻塞IO：少量线程处理大量连接，资源消耗恒定
2. 背压机制：消费者可以控制流速，避免被撑爆
3. 链式调用，逻辑清晰
4. HTTP 2支持：多路复用，忽略连接数限制
### 简单实现

```java
/**
 * 简单的Flux流式响应
 * Spring WebFlux 会自动将 Flux<String> 转换为 SSE 格式
 */
@GetMapping(value = "/stream", 
		   produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> streamFlux() {
	return Flux.interval(Duration.ofSeconds(1))  // 每秒一个数据
			   .map(seq -> "数据流 #" + seq)
			   .take(10);  // 发送 10 条后自动结束
}
```
### 踩过的坑🕳

WebFlux的前提是**全链路非阻塞**。如果在Flux里调了一个阻塞方法，比如JDBC查询，整个事件循环会被卡住。
```java
return Flux.create(sink -> {
    String result = userService.query();  // 阻塞！
    sink.next(result);
});
```
正确的做法应该是包装为异步：
```java
return Mono.fromCallable(() -> blockingService.query())
    .subscribeOn(Schedulers.boundedElastic());  // 切到弹性线程池
```

调用AI进行流式回复的过程中，如果需要对服务进行回调，例如对token进行统计，也可以使用`Flux.defer()`进行内部懒加载，能够保证多订阅者隔离。

```java
@Override
public Flux<String> generateSqlStream(String promptStr, Consumer<Integer> tokenUsageCallback) {
	Prompt prompt = new Prompt(promptStr);
	return Flux.defer(() -> {
		JsonStreamParser parser = new JsonStreamParser();
		AtomicInteger maxTokens = new AtomicInteger(0);
		return chatClient.prompt(prompt)
				.stream()
				.chatResponse()
				.doOnNext(response -> {
					if (response.getMetadata() != null && response.getMetadata().getUsage() != null) {
						Integer totalTokens = response.getMetadata().getUsage().getTotalTokens();
						if (totalTokens != null) {
							maxTokens.set(Math.max(maxTokens.get(), totalTokens.intValue()));
						}
					}
				})
				.doOnComplete(() -> {
					if (maxTokens.get() > 0 && tokenUsageCallback != null) {
						tokenUsageCallback.accept(maxTokens.get());
					}
				})
				.flatMapIterable(response -> {
					String chunk = response.getResult() != null && response.getResult().getOutput() != null ? response.getResult().getOutput().getText() : "";
					return parser.processChunk(chunk);
				})
				.concatWith(Flux.defer(() -> Flux.fromIterable(parser.processComplete())));
	});
}
```

传统思维的坑：
```java
JsonStreamParser parser = new JsonStreamParser();
AtomicInteger maxTokens = new AtomicInteger(0);

return chatClient.stream().doOnNext(response -> maxTokens.set(...));
```
这样子看起来没问题，但如果两个用户同时调用这个方法：用户A的流更新了maxTokens，用户B的流也同时更新了maxTokens，统计就乱了。

WebFlux的方法：
```java
Flux.defer(() -> {
    // 每次订阅时才执行
    JsonStreamParser parser = new JsonStreamParser();
    AtomicInteger maxTokens = new AtomicInteger(0);
    return ...;
});
```
`defer()`的意思是“等有人订阅再说”，每次调用`.subscribe()`，都会重新执行`defer`里的逻辑，创建独立的`parser`和`maxTokens`。

这就是WebFlux的核心特性之一：**Flux是冷流，没人订阅就不执行，每次订阅都独立执行**。

*那问题又来了，我也没看到有谁.subscribe()订阅呢？*

确实，在执行这段代码时，什么也不会发生：
```java
public Flux<String> generateSqlStream(...) {
    return Flux.defer(() -> {
        // ...
        return chatClient.stream()...;
    });
}
```
没有请求发出，没有LLM调用，没有数据流。`Flux`只是一个定义，或者说一张配方，描述了数据会如何流动。必须有人调用`.subscribe()`，配方才会变成真正的执行。那订阅在哪？

1. Spring替我们做了
	对于service方法`generateSqlStream`，会通过Controller接收前端请求调用，返回一个`Flux<String>`，当Spring检测到返回类型是`Flux`时，自动设置`Content-Type: text/event-stream`，框架调用 `.subscribe()`，开始执行流，每个元素通过HTTP连接写回给前端。
	```java
	@RestController
public class ChatController {
    
    @GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> chat(@RequestParam String prompt) {
        return chatService.generateSqlStream(prompt, tokenUsage -> {
            log.info("Token用量: {}", tokenUsage);
        });
    }
}
	```
	
2. 手动调用
	如果这个方法在Service层被其他代码调用，就要通过手动subscribe执行
	```java
	flux.subscribe(
    chunk -> System.out.println("收到: " + chunk),  // onNext
    error -> System.err.println("出错: " + error),   // onError
    () -> System.out.println("完成")                  // onComplete
);
	```
	如果只是拿到Flux，并不会执行
	```java
	Flux<String> flux = chatService.generateSqlStream("查询所有用户，按id倒排", null);
	```

## WebSocket

它的本质是双向通信协议，服务端和客户端可以互相发消息。底层是TCP连接，握手阶段用 HTTP，之后升级协议。
理论上很美好：
- 双向实时通信
- 低延迟（不需要HTTP头）
- 真正的长连接
实际很复杂，连接状态、心跳、重连都得自己实现，协议兼容问题等...只有当真的需要双向通信时才用WebSocket。比如：协作编辑、实时交互游戏等，如果只是服务端单向推送，WebSocket属于杀鸡用牛刀，SSE或WebFlux更合适
### WebSocket连接建立的流程

整个流程通常叫**WebSocket握手（Handshake）**，主要分为**客户端发起→服务器响应→升级协议→建立长连接**。
1. 客户端发起
   客户端在建立WebSocket连接时，先发送一个HTTP GET请求，请求头中会包含升级协议信息：
   ```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket  # 请求将协议升级为WebSocket
Connection: Upgrade  # 告诉服务器需要升级连接
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==  # 客户端随机生成的Base64字符串，用于服务器生成响应验证
Sec-WebSocket-Version: 13  # WebSocket协议版本
Origin: http://example.com
   ```
   初始握手还是HTTP协议，所以可以穿过普通HTTP代理。
2. 服务器响应
   服务器收到请求后，如果支持WebSocket协议，会返回101 Switching Protocols，确认协议升级：
   ```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
   ```
   服务器会用客户端的`Sec-WebSocket-Key`+GUID`"258EAFA5-E914-47DA-95CA-C5AB0DC85B11"`做SHA-1哈希，再Base64编码生成`Sec-WebSocket-Accept`。
3. 升级协议
4. 建立长连接
   握手成功后，HTTP连接升级为TCP长连接，客户端和服务器之间的通信不再是HTTP请求/响应，而是 **WebSocket帧（Frame）**；每条消息被封装成WebSocket Frame，包括了：
   + 文本帧（UTF-8字符串）
   + 二进制帧（图片、音频等）
   + 控制帧（关闭连接、ping/pong心跳）
5. 连接关闭
   双方任意一方发送Close Frame，对方返回确认帧，TCP连接关闭

## Spring AI的流式方案

如果用 Spring AI，流式输出已经封装好了：
```java
@GetMapping("/chat")
public Flux<String> chat(@RequestParam String message) {
    return chatModel.stream(message)
        .map(response -> response.getResult().getOutput().getContent());
}
```
一行代码，返回的是`Flux<String>`，前端直接订阅。Spring AI内部处理了流式API调用、错误重试等机制，但底层还是WebFlux，所以响应式编程的坑一样存在。
